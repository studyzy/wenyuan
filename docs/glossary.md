# 文渊英文术语表（面向后台开发者的理解指南）

> 写给"不是搞 AI 系统、也不是搞脑科学"的普通后台程序员。
>
> 文渊是参考实现（reference implementation）的兼容移植：API、PostgreSQL schema 与领域术语完全一致。本文所有术语均先在参考实现源码与文档中核对过含义，再写解释；频次来自对参考实现仓库约 4500 个代码/文档文件的实际词频统计（`git ls-files` 全量扫描，排除 generated / node_modules / lock）。排序按 **频率 × 重要性** 综合，而不是单纯字面出现次数。
>
> 排序逻辑：先按"读这个系统时你最绕不开它"的等级分档（★★★ 核心概念 / ★★ 重要机制 / ★ 支撑设施），档内再按词频降序。

## 0. 先建立一个心智模型（读术语表之前）

如果你是后台开发，你已有的知识几乎可以直接平移。这个系统可以粗看成：

```
你熟悉的                               文渊里的说法
─────────────────────────────────────────────────────────────
PostgreSQL 里的一张表 + 行             bank（记忆库）
写接口 POST                            retain（写入/记忆）
查询接口 SELECT + 搜索                 recall（检索/回忆）
你写的定时任务汇总报表                 consolidation（巩固）
一个"按问题缓存好答案"的物化视图        mental model（心智模型）
配置项（per-tenant / per-bank）         disposition / mission / directive
消息队列 + worker + 任务状态表          async operations（异步操作）
多租户 schema 隔离                      tenant（租户）
```

**唯一真正"不像后台"的东西**是：这个系统的"写入"和"检索"中间夹了一堆 **LLM（大模型）调用**。传统后台你写什么就存什么；这里你写入一段文本，系统会用大模型先把它**抽成结构化的事实**，再用向量模型算**语义坐标**，最后把结果存进 Postgres。理解这一点，后面所有术语都不难。

---

## 1. 第一梯队的五个词（★★★，不搞懂这五个，后面的都白看）

### 1.1 Bank（记忆库）—— 出现 ≈28,000 次，约 2,200 个文件

**短译：记忆库 / 记忆空间**

**详细解释：** Bank 是文渊里**最高层的隔离单位**，直译"银行"其实是财会的"钱库"隐喻——一个存放记忆的独立仓库。你完全可以把它理解成**一个独立的数据库 / 一个独立的租户库**：里面的数据、配置、身份、知识全部自成体系，bank 之间严格不串数据。

每个 bank 有自己的：
- **身份**（mission，见 2.4）和**性格**（disposition，见 3.1）
- **知识**（facts → observations → mental models 三层，见 1.3 和 3.4）
- **配置**（用哪个 LLM、多大的 chunk、检索预算多少）

API 形态就很能说明问题：所有接口都长这样 `/v1/default/banks/{bank_id}/memories/recall`——**一次请求只操作一个 bank**，跨 bank 的编排是调用方的责任，服务端不做。这正是你熟悉的多租户设计。

**对你意味着什么：** 一个 coding agent 接入时通常会按 **repo 名**派生一个 bank（比如 `repo:my-project`），所以"这个仓库的记忆"就等价于"这个 bank 里的数据"。排查问题时第一件事永远是确认 bank_id 对不对。

---

### 1.2 Retain（记忆 / 写入）—— ≈14,500 次，约 1,980 个文件

**短译：记忆、存入、保留**

**详细解释：** Retain 是**写入侧的总称**，语义上对应你的 `POST`。但和普通 `INSERT` 有两个本质区别：

1. **它不是"存原文"，而是"先理解再存"。** 你 retain 一段对话，系统会先用 LLM 把它拆成一条条**事实（fact）**，比如 "Alice 去年春天加入了 Google" 会被拆成"Alice 加入了 Google"+"时间是去年春天"，还会附带抽取情绪、动机、推理原因。
2. **它是流水线，不是单条 SQL。** 一次 retain 依次经过：切块（chunk）→ LLM 抽事实 → 实体抽取与归一 → 生成向量 → 落库 → 软链接建图 → **入队异步巩固**。

**重要细节：** retain 默认是**异步**的。请求返回的常常是一个 operation id，真正的处理由 worker 在后台完成。这和你熟悉的"投递消息进队列"是一个模型。

**易混点：** `retain` 存的是**从原文提炼出的事实**；原文本身存在 `documents` / `chunks` 表里，后面"chunks"那一节会讲。

---

### 1.3 Recall（检索 / 回忆）—— ≈13,570 次，约 1,780 个文件

**短译：检索、回忆**

**详细解释：** Recall 是**读取侧的总称**，对应你的 `SELECT` + 搜索。但它是**四路并行检索 + 融合**，而不是单一查询：

| 检索臂 | 直白解释 | 后台类比 |
|---|---|---|
| **Semantic**（语义） | 按"意思相近"找，不靠字面 | 向量相似度检索 |
| **BM25**（关键词） | 按字面精确匹配专有名词、代码标识符 | 全文索引（`tsvector` 等） |
| **Graph**（图） | 顺着实体之间的关系跳转 | JOIN 一张图，多跳 |
| **Temporal**（时间） | 解析 "last spring" 这类时间，按时间窗过滤 | `WHERE created_at BETWEEN ...` |

四路结果再用 **RRF（倒数排名融合）** 合成一份，再用 **cross-encoder** 重排，最后按 **token 预算**截断返回。

**最关键的一点（后台程序员最容易忽略）：** recall 的返回量不是"top-k 条数"，而是 **token 预算**（默认 4096 tokens）。因为调用方是 LLM，LLM 的上下文窗口按 token 计量，不是按"行数"计量。所以"返回 100 条"这种思维在这里是错位的——是"填满 4096 个 token 为止"。

**另一个细节：** `budget`（low/mid/high）控制的是**搜得多深**（图跳几跳、候选池多大），`max_tokens` 控制的是**吐多少**。这两个是**独立维度**，别混。

---

### 1.4 Reflection / Reflect（反思 / 推理）—— ≈8,420 次，约 1,250 个文件

**短译：反思、（带人设的）推理**

**详细解释：** 如果 recall 是"查资料"，reflect 就是"**拿着资料思考并回答**"。它是一个 **agentic loop（智能体循环）**——LLM 在这个循环里有工具可调，自己决定下一步查什么：

1. 先查 **mental models**（别人预先写好的答案）
2. 再查 **observations**（系统巩固出来的信念）
3. 最后才回落到 **raw facts**（原始事实，用作事实核对）
4. 最多 10 轮迭代，然后必须给出**带引用**的答案

**和你熟悉的东西的差异：** 普通接口是"一次查询→返回结果"。这里是"一个循环，模型自己决定调几次工具"。所以 reflect 是**贵且慢**的（要多次 LLM 调用），这也正是为什么要用 mental model 把它"预计算"掉。

**"reflection" 里的心理学词汇不要当真：** 它不是说系统有意识，而是借用认知科学的名字描述"系统对自身积累的知识做一次复盘、归纳、再表达"。**Disposition（人设）** 只影响 reflect，不影响 recall——这是一条很重要的边界，文档里明确写了。

---

### 1.5 Memory（记忆）—— 贯穿全系统的根词

**短译：记忆**

**详细解释：** "Memory" 在这个仓库里指的不是内存（RAM），而是**给 AI 智能体用的长期知识存储**。整个项目的定位就是"AI agent 的长期记忆系统"。

一个关键的层级概念（**务必记住这三层，很多术语都挂在这上面**）：

```
raw fact（原始事实）        ← retain 抽出来的，一条一句话，最细
      ↓ 巩固 consolidation
observation（观察/信念）    ← 多条事实归并去重后的"信念"，带证据
      ↓ 门槛更高、人工/定时策展
mental model（心智模型）    ← 一个问题的完整答案，是一整篇文档
```

越往下越"沉淀"、越便宜、越稳定。reflect 是按**从上到下**的顺序去找的。

## 2. 第二梯队：频繁出现且直接决定系统行为的机制（★★）

### 2.1 Fact（事实）—— ≈6,600 次

**短译：事实**

**详细解释：** retain 流水线用 LLM 从原文里抽出来的最小知识单元，通常一句话一条。事实有两种类型，**按"谁在说话"划分，而不是按语法**：

| 类型 | 含义 | 例子 |
|---|---|---|
| **world**（世界事实） | 关于外部世界/他人/事物 | "Alice 在 Google 工作" |
| **experience**（经验事实） | **这个 bank 自己的 agent** 做过/看到的事 | "我向 Alice 推荐了 Python" |

**易错点：** 用户对 agent 说 "I bought a Tesla"，这是 **world** 事实（关于用户），不是 experience（因为说话的不是 agent 本身）。这个区分靠句子的"视角"判断，是 LLM 干的活。

### 2.2 Document / Chunk（文档 / 切块）—— document ≈8,400 次，chunk ≈2,780 次

**短译：文档 / 切块**

**详细解释：** 你 retain 进来的一份原始材料（一段对话、一个文件，或大量文本）会被存成 **document**，并切成多个 **chunk**（分块），因为长文本没法整段塞进模型。这是 RAG 体系里的标准做法，你作为后台开发可以理解为**大字段的物理分片**。

**为什么要知道它：** recall 时可以传 `include_chunks=True`，把"提炼后的事实"**回溯到它对应的原文片段**。因为事实是提炼过的、简洁但会丢细节；需要"原话怎么说"时就靠 chunk。

### 2.3 Consolidation（巩固）—— ≈5,260 次

**短译：巩固、（知识）合并加工**

**详细解释：** 这是**后台异步任务**：把新产生的一批事实和已有的 observations 做比对、归并、去重、演化。类比你的"定时任务把散落明细汇总成统计表"。

特征：
- **自动**：retain 完成后自动触发（由 worker 异步跑，不是内联）
- **增量演化**：不是覆盖，而是"加固 / 削弱 / 推翻"已有的观察，并**保留历史**
- **近似去重**：两个说法略有差异的观察，会比较相似度决定"合并"还是"保留"，阈值默认 `0.97`

> 注意一个"坑"（文档里有专门写）：去重只在**同一 tag 作用域内**进行。如果你每次 retain 都打一个唯一的 `session-id` tag，那每次会话都各成一个作用域，永远互相不去重，最后会得到一堆重复观察。要跨会话合并需用 `observation_scopes: "shared"`。

### 2.4 Observation（观察 / 信念）—— observations ≈4,930 + observation ≈4,530 次

**短译：观察、巩固后的信念**

**详细解释：** consolidation 的产出物。它**不是随便一句总结**，而是：

- **有证据**：每条 observation 都挂着支撑它的**原始记忆 ID 和原文引用**
- **有证明计数**：多少条事实支撑它
- **会演化**：新证据来了是"精化"而不是"覆盖"
- **有 Freshness（新鲜度）**：如果新记忆还没被巩固进去，reflect 会把相关 observation 标记为**陈旧（stale）**，然后回头去核对原始事实

这是整个系统里"最像数据仓库物化视图"的东西。

### 2.5 Entity（实体）—— ≈3,720 次

**短译：实体**

**详细解释：** 文本里出现的**人、组织、地点、产品、概念**——和你做业务系统时的"业务实体"是同一个概念。"Alice"、"Google"、"Python" 都是实体。

关键机制 **Entity Resolution（实体解析/归一）**：同一个人的不同写法要合并成一个：
- "Alice" + "Alice Chen" + "Alice C." → **模糊名字匹配（fuzzy name matching）** 合并为一个实体
- 再叠加**共现（co-occurrence）上下文**做消歧：如果某 "Alice" 老是和 Google、Stanford 一起出现，那她大概率是同一个人
- **反向风险**：解析是"判断"，会判错——历史上的短名字可能被吸收进一个无关的已有实体。文档里明确承认这点并给了调参项

这直接支撑了 recall 的**图检索**：事实之间通过实体连成图，所以你问 "Alice 的上级的团队在做什么"能跳过去。

### 2.6 Mental Model（心智模型）—— mental ≈5,830 + mental_model ≈3,640 次

**短译：心智模型**

**详细解释：** 直白说：**一个问题的"已写好的、自动保鲜的答案"**。

它在心理学里指"人对世界的内部认知框架"，在这里被借用为：**围绕一个固定问题预先合成的一整篇文档**。你定义问题（"这个项目有哪些组件？"），系统在后台把答案写好、存起来、并在知识变化时**自动重写**。

**三个特性决定了它为什么值钱：**
1. **省时**：拿到它是一次数据库读，不触发检索、不触发 LLM，毫秒级
2. **一致**：只有一份文档，所以两个用户问同一个问题必得同一个答案（而不是两次各自生成的、可能互相矛盾的答案）
3. **增量刷新**：不是整篇重写（LLM 整篇重写会悄悄漂移），而是**只改需要改的部分**

**它的局限也要知道**：它可能"落后"。所以模型带一个新鲜度信号，落后的模型仍会展示给 reflect，但**不再能短路检索**——必须回去核对下层事实。

### 2.7 Knowledge Page（知识页）—— knowledge ≈3,410 次

**短译：知识页**

**详细解释：** **Knowledge page 就是一个"简化版的 mental model"**——同样的合成、同样的后台刷新、同样的来源追踪。区别只是**用户需要知道的细节更少**：你只提供"名字 + 一个问题"，其余决策（读什么、何时重建、怎么改）全部走默认值。

它的形态是 **wiki**：页面放在文件夹树里，可浏览、可搜索，还能 `wenyuan-admin fs mount` **映射成磁盘上真实的 markdown 文件**（这对 coding agent 特别友好——agent 天生会用 `ls` / `grep` / `cat`）。

一句话记忆：**"形状是 wiki，底层是 memory。"**

### 2.8 Token / Budget（Token / 预算）—— token ≈3,510 + budget ≈5,300 次

**短译：词元 / 预算**

**详细解释：** 
- **Token（词元）** 是 LLM 处理文本的最小单位。大致：英文 1 个 token ≈ 0.75 个单词，中文 1 个汉字 ≈ 1~2 个 token。**它就是 LLM 的"计费单位"和"上下文容量单位"**——相当于 LLM 世界里的"字节数"。
- **Budget（预算）** 在这里有两个含义，别混：
  - **检索预算（budget 参数）**：low/mid/high，控制**搜得多深**
  - **Token 预算（max_tokens）**：控制**返回多少内容**

系统的核心设计理念写在文档里：**"文渊 is built for AI agents, not humans"**——传统系统按"返回 top-k 条"设计，但这个系统按"填满多少个 token"设计，因为消费方是 LLM。

### 2.9 Embedding（向量嵌入）—— embedding ≈2,510 + embeddings ≈2,120 次

**短译：向量嵌入 / 嵌入向量**

**详细解释：** 用**向量模型**把一段文本变成一串浮点数（一个高维坐标）。语义相近的文本，坐标也相近。所以"查相似"就变成了"算向量距离"——这一步是语义检索（Semantic arm）的全部原理。

**后台类比：** 你可以把它理解成"把文本哈希成一个**保留语义**的定长值"，然后建 ANN （近似最近邻）索引来查。数据库侧用的是 **pgvector**（Postgres 的向量扩展）。

文渊的部署接线：外部 **TEI** 服务托管 `intfloat/multilingual-e5-small`（384 维，查询带 `query: `、入库带 `passage: ` 前缀），模型由 TEI 侧提供，本机不下载、不加载。

### 2.10 Reranker / Cross-Encoder（重排器 / 交叉编码器）—— reranker ≈1,780 + cross_encoder ≈1,080 次

**短译：重排器、交叉编码器**

**详细解释：** 两段式检索的**第二段**。

- **第一段（粗排）**：向量/BM25 快速召回一大堆候选
- **第二段（精排）**：**Cross-Encoder** 把「查询」和「候选」**拼在一起**喂给模型，逐对打分，重新排序

**为什么需要它：** 粗排的向量是"两边分别编码再比距离"，快但粗；cross-encoder 是"两者一起看"，准但贵——所以只能对少量候选做。

文渊的部署接线：TEI 服务托管 `BAAI/bge-reranker-base`。

### 2.11 RRF / Fusion（倒数排名融合）—— fusion ≈340 + rrf ≈650 次

**短译：倒数排名融合**

**详细解释：** 把 4 路检索结果合成一份的算法。核心公式（标准化写法）：

```
score(d) = Σ_i  1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在第 i 路检索里的排名，`k` 是平滑常数（通常 60）。

**两条关键设计：**
- **看排名，不看分数**——因为 4 路检索的分数量纲完全不同（向量距离 vs BM25 分数 vs 图距离），分数无法直接比，但"排第几"可比。这和你做"多路召回合并"时的思路一致。
- **多票者胜**——一个结果在越多路里出现，排名越靠前（共识）。

### 2.12 Temporal（时序 / 时间）—— ≈1,720 次

**短译：时间维度、时序**

**详细解释：** 系统会**解析查询里的时间表达**（"last spring"、"2023 年"、"在 Alice 加入之前"）成时间区间，再按时间过滤检索。这就是为什么它能回答 "Alice 去年春天做了什么"，而普通向量检索只会返回所有关于 Alice 的东西。

文档里还有个细节值得知道：时间窗内选候选是**按相关度优先，而不是按新旧**——避免"最近的不相关记忆"把相关的挤掉；同时会在时间窗内**分桶取样**，保证覆盖整个区间而不是挤在某一小段。

### 2.13 Local / Provider（本地 / 服务商）—— local ≈3,410 次

**短译：本地（推理）/ 服务商**

**详细解释：** 系统里几乎所有模型都有两种跑法：
- **local（本地）**：本机加载模型跑（如 SentenceTransformers / ONNX / flashrank）。**免费、隐私好、但吃 CPU/显存**。
- **remote / provider（远程）**：调外部 API（OpenAI / Cohere / TEI 等）。**快、不占本机资源，但花钱、有网络依赖**。

这是**部署时最需要决定的一组参数**。参考实现的默认全是 local；文渊按本仓库的部署约定接外部 **TEI** 服务（`embeddings.tei_url` / `reranker.tei_url` 指定主机），完全不配置模型时走无模型的确定性路径（`none`）。

### 2.14 Worker / Async Operation（工作进程 / 异步操作）—— worker ≈3,120 + async_operations ≈890 次

**短译：工作进程、异步任务**

**详细解释：** 这是**你作为后台开发最熟悉的部分**，几乎是教科书式的队列实现：

- API 收到需要后台处理的请求 → 往 `async_operations` 表**写一行**（同事务）
- **Worker** 进程轮询这张表，用 `FOR UPDATE SKIP LOCKED` **认领任务**（经典的 Postgres 当队列的写法，避免锁争抢）
- 任务状态机：`pending / running / completed / failed / cancelled`，失败按 `WENYUAN_API_WORKER_MAX_RETRIES` 重试
- 支持**父子任务**（批量操作会派生子任务）
- 支持**幂等重试**：retain 可带 `operation_id`，重复提交同一 id 不会重复处理

排查线上问题时，`async_operations` 表是你第一个该看的地方。

### 2.15 Disposition（性格 / 人设）—— ≈1,470 次

**短译：秉性、人设**

**详细解释：** 三个 1~5 分的**数值参数**，决定 reflect 的"性格"：

| 参数 | 中文 | 低分表现 | 高分表现 |
|---|---|---|---|
| **Skepticism** | 怀疑度 | 信任、照单全收 | 质疑、要求证据 |
| **Literalism** | 字面主义 | 灵活解读、能读弦外之音 | 严格照字面理解 |
| **Empathy** | 共情 | 冷淡、只看事实 | 体察情绪语境 |

**重要边界：disposition 只影响 reflect，不影响 recall。** 同样的记忆，两个人设相反的 bank 会得出不同结论——这是刻意设计（"same facts → different conclusions because disposition shapes interpretation"）。

这和 **Directive（指令，≈1,320 次）** 要区分开：disposition 是**软性影响**（风格），directive 是**硬性规则**（必须遵守，比如"绝不推荐具体股票"）。

### 2.16 Bank Template（记忆库模板）—— ≈245 次

**短译：记忆库模板**

**详细解释：** 创建新 bank 时用的**配置预设**。类比：K8s 的 Pod template、或者你项目里的"默认配置文件"。它把 mission / disposition / 各种阈值打包成一个模板，新建 bank 时引用即可，避免每个 bank 手写一堆配置。

## 3. 第三梯队：基础设施与周边（★，见到能认出即可）

### 3.1 Tenant / Schema（租户 / 模式）
**短译：租户 / 数据库模式**
多租户隔离机制。`TenantExtension` 负责校验请求并**决定用哪个 PostgreSQL schema**——隔离做在**数据库层面**，不是应用层面。默认 built-in 实现是 `ApiKeyTenantExtension`（校验 API key，统一走 `public` schema）；静态多用户可用 `StaticKeysTenantExtension`（每个用户一个 `{prefix}_{user_id}` schema）。

### 3.2 Harness（宿主 / 智能体宿主）—— ≈2,010 次
**短译：宿主智能体、外部代理程序**
这个词在 coding agent 语境里指**"跑 AI 的那个外部程序"**——Claude Code、Codex CLI、Cursor CLI、opencode 等。文渊提供一套"壳"，适配到不同的 harness 上。**它和 AI 模型本身无关**，指的是"那个调用模型的客户端程序"。
类比：harness 是"驱动"，模型是"引擎"。

### 3.3 Hook / Session / Transcript（钩子 / 会话 / 会话记录）
- **Hook（钩子，≈2,620 次）**：宿主程序在特定生命周期点回调你的函数。coding agent 只用三个阶段：`sessionStart`（会话开始）、`prompt`（用户提交 prompt，**只读**）、`stop`（会话结束，**唯一的写入点**）
- **Session（会话，≈4,930 次）**：一次对话
- **Transcript（会话记录，≈1,500 次）**：会话的原始 JSONL 文件。**注意：解析时会丢弃子代理（`isSidechain`）、元信息（`isMeta`）、tool_result 等内容**，只保留人说话和"动作摘要"

### 3.4 MCP（Model Context Protocol，模型上下文协议）—— ≈4,600 次
**短译：模型上下文协议**
一个**开放协议标准**，让 AI 助手能以统一方式访问外部工具/数据源。作用类似"AI 世界的 JDBC"——定义一种通用接口，任何 AI 客户端都能接任何工具服务。文渊自带一个 MCP server，挂在 `/mcp/{bank_id}/`，让 AI 助手直接存取记忆。

### 3.5 Mission（使命 / 身份）—— ≈2,270 次
**短译：使命**
用**一段自然语言**描述这个 bank "是谁、在乎什么"。它影响：
- `reflect_mission`：影响 reflect 的推理
- `retain_mission`：影响 retain 抽什么事实
- `observations_mission`：影响巩固成什么样的观察
**注意三个 mission 是分开的，别以为设一个就全生效。**

### 3.6 Directive（指令 / 硬规则）—— ≈1,320 次
**短译：指令、硬规则**
reflect 时**必须遵守**的规则。`tags` 决定何时生效：无 tag = 全局永远生效；有 tag = 仅当请求带匹配 tag 才生效。和 disposition 的区别见 2.15。

### 3.7 Webhook（回调）—— ≈1,160 次
**短译：网络回调**
异步操作完成时主动通知你的 HTTP 回调。你熟悉的东西，不赘述。

### 3.8 Graph Maintenance（图维护）—— ≈253 次
**短译：图维护**
周期性后台任务，负责维护实体关系图（清理、修剪、保持图不膨胀）。属于 MaintenanceLoop 定时循环的一部分。

### 3.9 RAG（Retrieval-Augmented Generation，检索增强生成）—— ≈272 次
**短译：检索增强生成**
一个通用范式：**先检索相关资料，再把资料塞进 LLM 上下文，然后再生成答案**。几乎所有"基于文档的 AI 问答"都是这么做的。
**文渊的定位是"RAG 更进一步"**：普通 RAG 只有语义检索、无状态、无遗忘与演化；文渊有四路检索 + 时序 + 实体图 + 知识巩固 + 持久状态。参考实现仓库里专门有一篇与 RAG 对比的文章做展开。

### 3.10 LiteLLM / Ollama / TEI / ONNX / FlashRank（各类具体实现）
**短译：具体工具名，不必逐个记**
- **LiteLLM**：一个统一封装 100+ LLM 服务商的库
- **Ollama / LM Studio**：本地跑开源模型的运行时
- **TEI（Text Embeddings Inference）**：HuggingFace 的向量服务
- **ONNX**：模型跨平台运行时格式
- **FlashRank**：一个轻量级重排库
**记住一句就够：这些都是"同一个位置的几种可插拔实现"，配置项切换而已。**

### 3.11 pgvector / Oracle 23ai
**短译：具体数据库**
- **pgvector**：PostgreSQL 的向量扩展，提供向量列类型和 ANN 索引（HNSW 等）
- **Oracle 23ai**：Oracle 的 AI 数据库，也支持向量
系统同时适配两者，迁移脚本通过 `run_for_dialect` 分派。

### 3.12 Benchmark 相关：BEAM / LoCoMo / LongMemEval / AMB / judge
**短译：基准测试**
- **AMB**：`agent-memory-benchmark`，评测数据集与评分工具的集合
- **BEAM / LoCoMo / LongMemEval**：三个记忆能力的评测数据集
- **LLM-as-judge（评审模型）**：用另一个 LLM 当裁判给答案打分。这是 AI 评测的标准做法，因为"答案对不对"没法字符串精确匹配
- **distractors（干扰项）**：评测里故意掺入的无关记忆，用来测检索精度

| 术语 | 短译 | 一句话 |
|---|---|---|
| **Prose / Verbatim** | 散文式 / 逐字 | prose 指合并成通顺段落的文本；verbatim 指原样保留、不改写 |
| **Multimodal** | 多模态 | 同时处理文本+图片等 |
| **Chunk size** | 切块大小 | 分块的字符/token 上限，影响检索粒度 |

## 4. 最容易混淆的六组词（重点防坑）

| 易混的两组 | 区别 |
|---|---|
| **Recall vs Reflect** | Recall 只**取回**资料（无 LLM 推理）；Reflect **带着人设推理并回答**（多次 LLM 调用） |
| **Observation vs Mental Model** | Observation 是**自动产生**的、一次只表达一个信念；Mental Model 是**你显式定义**的、覆盖一个问题的整篇文档 |
| **Budget vs Max-tokens** | Budget 管"**搜多深**"；Max-tokens 管"**吐多少**" |
| **Disposition vs Directive** | Disposition 是**软性风格影响**；Directive 是**硬性必须遵守** |
| **Fact vs Chunk** | Fact 是**提炼后**的一句结论；Chunk 是**原文分片**，可回溯源文 |
| **Bank vs Tenant** | Bank 是**记忆隔离单位**（应用概念）；Tenant 是**数据库 schema 隔离单位**（部署概念） |
